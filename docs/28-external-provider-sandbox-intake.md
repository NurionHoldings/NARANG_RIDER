## 공통 요청자료

1. 공식 API 문서, OpenAPI·JSON Schema·이벤트 스키마와 현재 버전
2. Sandbox URL, 테스트 계정 신청·승인 절차, 합성 테스트 데이터
3. 인증·권한 범위, 웹훅 서명, 키 교체·폐기 절차
4. 고정 IP 허용목록·mTLS·인증서 발급과 갱신 조건
5. 호출한도, SLA, 오류모델, 멱등성, 순서보장, 버전·지원종료 정책
6. 처리 필드별 목적·보존기간·국외이전·재위탁자
7. 웹훅 재전송·중복·순서역전·Replay 방지 계약
8. 보안·개인정보·장애 대응 연락창구와 통지 SLA
9. Sandbox·운영 가격표, 약관, DPA·SLA·라이선스 문서

## 안전한 제출

- 운영 비밀값, 개인키, 실제 고객·점주·라이더 개인정보와 운영 주문을 저장소·이메일·메신저로 보내지 않는다.
- 자격증명은 승인된 보안채널에서만 교환하고 저장소에는 vault 참조만 기록한다.
- 문서는 공식 HTTPS 원문 URL, 발행·만료일, SHA-256, 공급자 등록 참조와 함께 제출한다.
- 허용 형식은 JSON, YAML, Markdown, 일반 텍스트, PDF다. 압축·실행파일은 받지 않는다.
- 수신물은 악성파일·비밀·개인정보 검사 후 격리되며 업로드만으로 신뢰하지 않는다.

## 운영자 조치 순서

1. 공급자를 내부 등록부에 만들고 provider-registry 참조를 부여한다.
2. 본 요청서를 공식 보안·기술 담당자에게 전달한다. 이 저장소는 발송하지 않는다.
3. 보안채널을 합의한 뒤 Sandbox 자격증명은 Vault에 직접 적재한다.
4. 수신 문서의 원문 URL·SHA-256·발행/만료·형식·악성파일 검사 참조를 등록한다.
5. 상태를 RECEIVED에서 QUARANTINED로 이동하고 clean-room 검토자를 분리한다.
6. 공식 출처·서명·스키마 호환성·데이터 조건을 확인해 VERIFIED 또는 BLOCKED로 판정한다.
7. 기존 Sandbox 인증 하니스를 합성 데이터로 실행한다.
8. 하니스 PASS 뒤 에테르니언과 운영자 최인석이 각각 승인해야만 CERTIFIED로 전환한다.
9. 만료·버전변경·재위탁자변경·사고 발생 시 인증을 중지하고 다시 격리한다.
10. 외부 조건이 모두 해소되기 전 출시 판정은 BLOCKED로 유지한다.

## Clean-room 원칙

공식 계약과 관찰 가능한 입출력만 근거로 독립 구현한다. 제3자 소스코드·비공개 구현을 복제하지 않으며, 출처 URL·조회일·문서 해시·가정을 기록한다. 공식 명세가 없거나 충돌하면 추정 구현을 인증하지 않고 차단한다.

이 문서는 외부로 자동 발송되지 않는다. 담당 운영자가 공급자 신원과 수신 채널을 확인한 후 사용한다.
